# Semantic v27：修复前的分层判断

每次遇到“漏抓、误判、重复、验收失败”时，先定位问题发生在哪一层，再决定是否改代码。不能用改提示词来掩盖采集或物化层的问题。

## 分层与处理边界

| 层 | 先检查什么 | 正确的修复位置 |
| --- | --- | --- |
| 采集/详情页 | 原始列表、详情是否完整，标题、日期、正文是否一致 | 专用适配器、分页、详情选择器；若原文没有，后层不能补造 |
| 主体识别 | 公司名是否被描述词、产品词、英文品牌黏连或截断 | `entity_ledger` 的主体候选、别名和归属边界 |
| 事件候选 | 原文是否已有明确动作、动作范围是否被“去年/之后”等时间限定词污染 | `action_span_ledger` 的动作语法、时间作用域和 host-grounding |
| MiniMax 裁决 | 候选有证据但被拒绝，或输出字段/主体不一致 | claim contract、host-mandatory 规则、修复调用；不先扩大提示词 |
| 去重与物化 | 同一事实的标题/正文/技术-产能重复是否合并，是否保留主体+事件+引文 | `_merge_events` 及其血缘审计；必要时才改事件合并策略 |
| 验收与报告 | 审计统计是否描述最终结果，是否把被合并的 claim 误报成“丢失” | 验收器和 audit schema，不改语义判断本身 |

## 当前版本的结论

* 36Kr 的“融资完成后”误接纳属于动作时间作用域和 host-mandatory 层，已在候选/裁决前修复；不是靠再加提示词解决。
* 36Kr 的两个 TDDI 量产 claim 与同一产能事实重复，属于去重物化层。它们现在记录为 `model_accepted_claim_ids`，并在 `suppressed_claim_ids` 中说明；最终 `accepted_claim_ids` 只包含实际物化事件的 claim。
* 晶泰/Unity 的主体问题属于实体层，已修复为“Unity中国”等具体主体；不应在 MiniMax 输出后用字符串替换补救。
* 工信部政策正文由确定性政策种子保留标题级事实；正文中大量任务细节不是企业招聘事件，不能为了提高 claim 数而强行交给 MiniMax。

## 审计字段契约

`accepted_claim_ids` 是最终事件数组中实际出现的 claim 并集；`model_accepted_claim_ids` 是 MiniMax/host fallback 的原始接受结果；`suppressed_claim_ids` 是被确定性合并、摘要去重或事件优先级规则抑制的差集。三者分开后，验收可以区分“模型拒绝”“基础设施失败”和“已接受但被合理合并”，避免把后处理误报为模型漏抓。

## 修复决策顺序

1. 先用原始网页、动作 ledger、实体 ledger 和最终事件做一条 claim lineage 对照。
2. 若原文没有候选，修采集或确定性候选层。
3. 若候选存在但主体/时间范围错，修实体或动作作用域层。
4. 若候选明确且主体正确但 MiniMax 拒绝，才修 host-mandatory/contract 或提示词。
5. 若模型已接受但最终没有独立事件，先检查是否是合理去重；只有确有不同主体或不同事实被合并，才改物化层。
6. 最后再改验收指标和报告，不能用改指标掩盖事实遗漏。
