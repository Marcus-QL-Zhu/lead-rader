# 两阶段具体岗位生成

## 为什么调整

此前流程先用规则把市场信号归入“研发、产品、供应链”等宽泛职能，再让
LLM 写广告。即使文案由模型生成，输入画像本身过宽，最终容易得到
“硬科技研发总监”“供应链总监”一类吸引力不足的职位。

## 新流程

```text
当日 Top Leads 与证据
→ 直接 LLM 第一阶段：逐家公司推测具体 Director+ 人才需求
→ 确定性验证并写入内部 company_demand_analysis
→ 按具体岗位重新聚合跨客户人才池主题
→ 直接 LLM 第二阶段：生成具体匿名广告与猎聘 JSON
→ 确定性契约、匿名、具体性和多样性校验
→ 如不合格，只允许一次有明确错误列表的修复调用
→ 保存 pending_approval
```

第一阶段为每家公司输出 0–3 个岗位；证据不足可以明确输出 0 个。每个岗位包含：

- 1–3 个具体 Director+ 标题；
- 具体业务使命和 why-now；
- 3–5 条预期结果；
- 3–5 条 must-have 候选人信号；
- 1–3 条 preferred 候选人信号；
- 可安全公开的具体技术/能力词；
- 一个建议城市；
- 推测与输入证据之间的 grounding。

泛化标题会被拒绝。公开广告必须自然包含至少两个前置具体性词，且同批标题、
人才画像和 payload 不得重复。

## 城市约束

猎聘 `cities` 字段仍采用数组以兼容现有 Skills，但数组长度必须严格等于 1：

```json
{
  "cities": ["深圳"]
}
```

空数组或 `["上海", "杭州"]` 均不能通过 Lead Rader 校验。

## 真实模型验收

旧版曾通过服务器 OpenClaw `main` Agent 完成一轮三家公司验收；当前实现已改为复用其凭证直接调用 LLM API。
第一次广告生成中有一条仍然过宽，确定性闸门识别后触发一次修复。最终得到：

- 机器人产业合作总监；
- 具身数据平台运营总监；
- 机器人灵巧手量产总监。

三条标题互不重复，均通过 Director+、匿名化、具体性、猎聘字段及单城市校验。
验收产物保存在本地忽略目录 `.acceptance/openclaw-json-review/`，没有发布到
猎聘，也没有部署服务器代码。
